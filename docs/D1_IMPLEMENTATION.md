# D1 文件交换与解析记账

日期：2026-10-20。对应 `DEVELOPMENT_SPEC_V0_2.md` 的第一阶段；不是 v0.2 全部完成。

## 当前实现

- `contracts.py`：`mta.messages`、`mta.analysis-result` 1.0 严格 JSON Schema；拒绝重复键、非有限数字、错误字段、无时区时间。接受完整 JSON 或单个完整 JSON 代码围栏，不猜测修复。
- `exchange.py`：SQLite 迁移 5、固定 dataset_id、递增事件序号、独立导出检查点、不可变请求快照、原子文件输出、恢复、取消、导入预检与事务应用。
- 消息保持 origin 身份，跨库往返不复制相同原始事件；同原始身份但内容改变会报错。外部文件来源隔离为禁用账号/范围，不修改真实账号的扫描游标。
- `exchange_results` 和 `event_consumptions` 保存解析尝试；`parsed_candidates` 保存待确认候选，不触发旧版 identity_key 任务归并。
- CLI 与本地 UI 的“数据交换”页，共用同一个服务层。

## 两种检查点不能混淆

邮箱/聊天扫描游标只代表原始消息已持久化。D1 导出检查点只代表某个来源选择通道的文件已输出。解析成功另由消费记录表示。

导出将消息从 `pending` 预留为 `awaiting_result`，并不记成功消费；同一事件不会同时被旧 Worker 和文件解析请求占用。旧 Worker 的过期响应不得覆盖新请求的所有权。

相对设计稿新增 `pending` 选择模式：忽略导出检查点，选择所有尚未解析、未被其他请求预留的事件，用于取消后重试。`incremental` 选择通道检查点之后的待解析事件；`range` 按可靠源时间 `[start,end)` 过滤。UI 日期结束日自动转换为北京时间次日零点；无可靠源时间的消息不会按导入时间冒充。

## 每个导出批次的文件

| 文件 | 用途 |
|---|---|
| messages.json | 可跨库导入的规范化消息，附件仅元数据 |
| analysis-request.json | 绑定事件、版本、提示词、返回格式的解析请求 |
| prompt.json / prompt.txt | 带版本的提示词及网页聊天文本 |
| analysis-result.template.json | 带请求绑定 ID 的返回模板，初始状态为 failed 占位 |
| messages.schema.json | 消息格式 |
| analysis-result.schema.json | 结果格式 |

导入后可另下载 `analysis-result.json`：只包含实际已导入的各事件最新结果；缺失项不会伪造成功。

同一幂等键与相同配置重试返回同一个批次；更改配置必须使用新键。文件写入失败保留 preparing 批次，检查点不前进，可以恢复输出。取消保留记录/文件，只释放尚未成功解析的事件，迟到回复不能继续应用。

## 导入规则

1. 预检检查 Schema、dataset/batch/request/prompt 绑定、事件/版本归属、重复 ID 和引用证据。
2. 显示将解析、待确认、失败、已应用及本文件未返回的事件。
3. 确认应用时再次检查当前状态，在单个数据库事务内写入；状态变化导致旧预检失效。
4. 相同结果重复应用为 no-op。失败可重试；已成功结果的不同内容不允许直接覆盖，显式纠错流程后续实现。
5. 有候选的有效结果进入业务待确认队列；无候选结果须解释原因。模型建议不是事项完成证明。
